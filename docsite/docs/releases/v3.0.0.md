# v3.0.0 – Unreleased

Komodo v3 changes the production Compose storage layout and the canonical host filenames. Review the [GitHub release](https://github.com/neurekadev/komodo/releases/tag/3.0.0) for the changelog when v3.0.0 is published.

## Upgrading to Komodo v3

The v3 templates use a shared Docker named volume mounted at `/data` in Core and Periphery. With `COMPOSE_PROJECT_NAME=komodo`, Docker names this volume `komodo_data`. Existing database volumes keep their v2 names.

This migration is operator-driven and deliberately leaves every v2 file, bind directory, and named volume in place for rollback.

:::warning
Do not run `docker compose down -v`, delete `komodo_keys`, or remove the old Periphery root until the v3 deployment has been fully verified.
:::

### 1. Record and back up the v2 deployment

Run the following commands from the v2 installation directory. Set `V2_COMPOSE_FILE` to the template currently in use:

```bash
export V2_INSTALL_DIRECTORY="$(pwd)"
export V2_COMPOSE_FILE=mongo.compose.yaml
# For FerretDB instead, use: export V2_COMPOSE_FILE=ferretdb.compose.yaml

docker compose -p komodo -f "$V2_COMPOSE_FILE" --env-file compose.env config --volumes | tee v2-volume-names.txt
docker compose -p komodo -f "$V2_COMPOSE_FILE" --env-file compose.env ps
docker volume ls --filter name=komodo_
```

Create and verify a database backup before stopping v2:

```bash
docker compose -p komodo -f "$V2_COMPOSE_FILE" --env-file compose.env exec core km database backup -y
```

Record the existing `PERIPHERY_ROOT_DIRECTORY` from `compose.env`; `/etc/komodo` was the default. Back up that directory, any separately mounted sync files, and any custom configuration or certificates outside it.

Back up the old keys volume to a host archive:

```bash
mkdir -p "$V2_INSTALL_DIRECTORY/migration-backups"
docker run --rm \
  --mount type=volume,src=komodo_keys,dst=/source,readonly \
  --mount type=bind,src="$V2_INSTALL_DIRECTORY/migration-backups",dst=/backup \
  alpine:3.22 \
  tar -czf /backup/komodo-keys-v2.tar.gz -C /source .

docker run --rm \
  --mount type=volume,src=komodo_keys,dst=/source,readonly \
  alpine:3.22 \
  sh -c 'cd /source && find . -maxdepth 1 -type f -exec sha256sum {} \; | sort' \
  | tee "$V2_INSTALL_DIRECTORY/migration-backups/komodo-key-checksums-v2.txt"
```

### 2. Stop v2 without deleting storage

```bash
docker compose -p komodo -f "$V2_COMPOSE_FILE" --env-file compose.env down
```

Do not add `-v`. Confirm the recorded database and `komodo_keys` volumes still exist.

### 3. Create the v3 data volume

Check that `komodo_data` is not an unexpected pre-existing volume, then create it:

```bash
docker volume ls --filter name=komodo_data
docker volume create komodo_data
```

If the listing already shows `komodo_data`, inspect it and stop if it contains unknown data instead of overwriting it.

### 4. Copy the old Periphery root

Set the exact old host bind path and verify it before copying. The source is mounted read-only:

```bash
export V2_PERIPHERY_ROOT=/etc/komodo
test -d "$V2_PERIPHERY_ROOT"

docker run --rm \
  --mount type=bind,src="$V2_PERIPHERY_ROOT",dst=/source,readonly \
  --mount type=volume,src=komodo_data,dst=/data \
  alpine:3.22 \
  sh -c 'cp -a /source/. /data/'
```

This preserves existing `repos`, `stacks`, `builds`, `backups`, and SSL material beneath the root of `komodo_data`.

### 5. Copy keys and optional Core data

Copy the v2 communication keys into `/data/keys`:

```bash
docker run --rm \
  --mount type=volume,src=komodo_keys,dst=/source,readonly \
  --mount type=volume,src=komodo_data,dst=/data \
  alpine:3.22 \
  sh -c 'mkdir -p /data/keys && cp -a /source/. /data/keys/'
```

If sync files were mounted separately in v2, copy them in the same way after replacing the example source path:

```bash
export V2_SYNCS_DIRECTORY=/path/to/old/syncs
test -d "$V2_SYNCS_DIRECTORY"

docker run --rm \
  --mount type=bind,src="$V2_SYNCS_DIRECTORY",dst=/source,readonly \
  --mount type=volume,src=komodo_data,dst=/data \
  alpine:3.22 \
  sh -c 'mkdir -p /data/syncs && cp -a /source/. /data/syncs/'
```

The old Core repository cache may be copied to `/data/repo-cache`, but it is safe to let Komodo regenerate it.

### 6. Download and configure the v3 files

Create a new directory so the v2 installation files remain untouched. Select either the MongoDB or FerretDB download:

```bash
mkdir -p "$V2_INSTALL_DIRECTORY/../komodo-v3"
cd "$V2_INSTALL_DIRECTORY/../komodo-v3"

curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/mongo.compose.yaml
# FerretDB alternative:
# curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/ferretdb.compose.yaml
curl -fsSL -o .env https://raw.githubusercontent.com/neurekadev/komodo/main/compose/compose.env
```

Edit `.env` and merge the existing database credentials, host, authentication, OAuth/OIDC, webhook, and other operator settings. Do not copy the obsolete v2 storage paths back into the file.

Find Docker's actual host volume root:

```bash
docker info --format '{{.DockerRootDir}}/volumes'
```

Set that absolute result as `PERIPHERY_DOCKER_VOLUME_ROOT`. Standard Docker normally uses `/var/lib/docker/volumes`; rootless and customized installations differ. This path must remain mounted at the identical absolute path inside Periphery and must not be redirected into `/data`.

### 7. Review and start v3

```bash
docker compose config
docker compose config --quiet
docker compose up -d
```

The `3` image alias becomes available when v3.0.0 is published. Before that release, these commands intentionally stop at the image pull rather than silently running another major version.

### 8. Verify the migration

Verify all of the following before removing any v2 storage:

- `docker volume ls --filter name=komodo_` shows the original database volumes and the new `komodo_data` volume.
- Core starts against the existing database and existing users can log in.
- Servers, stacks, repositories, builds, procedures, variables, and other resources are present.
- Checksums for `core.key`, `reporting.key`, and `periphery.key` match the pre-migration files where those files previously existed.
- `/data/stacks`, `/data/repos`, `/data/builds`, `/data/backups`, `/data/syncs`, and `/data/ssl` contain the expected migrated content.
- Core and Periphery reconnect without generating replacement identities.
- The Stack File Manager can browse managed stack files.
- The Docker-volume File Manager can browse a named volume using the configured host Docker volume root.

Compare the migrated keys with the checksums recorded before the migration:

```bash
docker run --rm \
  --mount type=volume,src=komodo_data,dst=/data,readonly \
  alpine:3.22 \
  sh -c 'cd /data/keys && find . -maxdepth 1 -type f -exec sha256sum {} \; | sort' \
  > "$V2_INSTALL_DIRECTORY/migration-backups/komodo-key-checksums-v3.txt"

diff -u \
  "$V2_INSTALL_DIRECTORY/migration-backups/komodo-key-checksums-v2.txt" \
  "$V2_INSTALL_DIRECTORY/migration-backups/komodo-key-checksums-v3.txt"
```

You can also inspect all migrated files without modifying them:

```bash
docker run --rm \
  --mount type=volume,src=komodo_data,dst=/data,readonly \
  alpine:3.22 \
  find /data -maxdepth 2 -mindepth 1 -print
```

### 9. Roll back if needed

Stop v3 without deleting its volume:

```bash
cd "$V2_INSTALL_DIRECTORY/../komodo-v3"
docker compose down
```

Return to the untouched v2 directory and start it with the original command:

```bash
cd "$V2_INSTALL_DIRECTORY"
docker compose -p komodo -f "$V2_COMPOSE_FILE" --env-file compose.env up -d
```

The v2 bind directory, `komodo_keys`, database volumes, and original files remain available. Keep them until the v3 deployment has been verified and retained for the rollback period appropriate to your environment.
