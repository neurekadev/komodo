# v3.0.0 – Unreleased

Komodo v3 changes the production Compose storage layout and the canonical host filenames. Review the [GitHub release](https://github.com/neurekadev/komodo/releases/tag/3.0.0) for the changelog when v3.0.0 is published.

## Upgrading to Komodo v3

The v3 templates share the Compose volume `komodo_data` between Core and Periphery at `/data`. Existing MongoDB or FerretDB database volumes keep their v2 names.

:::danger Back up your deployment
Back up the database, `/etc/komodo`, the `komodo_keys` volume, and any custom configuration or certificates before continuing. The migration below moves files out of their v2 locations and assumes `komodo_data` does not already contain another deployment.
:::

### 1. Stop Komodo v2

Run the original v2 command from the installation directory, without `-v`:

```bash
docker compose -p komodo -f mongo.compose.yaml --env-file compose.env down
```

If you use FerretDB, replace `mongo.compose.yaml` with `ferretdb.compose.yaml`.

### 2. Move the v2 data into `komodo_data`

Create the v3 data volume with the labels Compose uses to identify its project and volume:

```bash
docker volume create \
  --label com.docker.compose.project=komodo \
  --label com.docker.compose.volume=data \
  komodo_data
```

Use one temporary Alpine container to move the Periphery root and communication keys into the new layout:

```bash
docker run --rm \
  --mount type=bind,src=/etc/komodo,dst=/v2-root \
  --mount type=volume,src=komodo_keys,dst=/v2-keys \
  --mount type=volume,src=komodo_data,dst=/data \
  alpine:3.22 \
  sh -eu -c '
    find /v2-root -mindepth 1 -maxdepth 1 -exec mv {} /data/ \;
    mkdir -p /data/keys
    find /v2-keys -mindepth 1 -maxdepth 1 -exec mv {} /data/keys/ \;
  '
```

The helper container is removed when it finishes. If v2 used a different `PERIPHERY_ROOT_DIRECTORY`, replace `/etc/komodo` in the bind mount. Move any separately mounted sync files or other custom data into the matching directory beneath `/data` before starting v3.

### 3. Install the v3 files

Rename the existing environment file so Docker Compose discovers it automatically:

```bash
mv compose.env .env
```

Download the v3 MongoDB template under its canonical host filename:

```bash
curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/mongo.compose.yaml
```

For FerretDB, download `ferretdb.compose.yaml` instead:

```bash
curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/ferretdb.compose.yaml
```

Keep the existing credentials and other operator settings in `.env`. Apply these storage-contract changes:

| Action | Variables |
| --- | --- |
| Remove | `COMPOSE_KOMODO_BACKUPS_PATH` |
| Change | `COMPOSE_KOMODO_IMAGE_TAG`, `KOMODO_PERIPHERY_PUBLIC_KEY`, `PERIPHERY_CORE_PUBLIC_KEYS`, `PERIPHERY_ROOT_DIRECTORY` |
| Add | `COMPOSE_PROJECT_NAME`, `KOMODO_PRIVATE_KEY`, `KOMODO_REPORTING_PRIVATE_KEY`, `KOMODO_CLI_BACKUPS_FOLDER`, `KOMODO_SYNC_DIRECTORY`, `KOMODO_REPO_DIRECTORY`, `PERIPHERY_PRIVATE_KEY`, `PERIPHERY_DOCKER_VOLUME_ROOT` |

Add or replace the settings using this exact block. Its comments and values match the current [`compose.env`](https://github.com/neurekadev/komodo/blob/main/compose/compose.env) example:

```dotenv
## Keep the established Compose project and named-volume prefix.
COMPOSE_PROJECT_NAME=komodo
## Follows "major.minor.patch" semver. Use the v3 major alias by default.
COMPOSE_KOMODO_IMAGE_TAG="3"

## Persist Core identity and reporting keys in the shared data volume.
KOMODO_PRIVATE_KEY=file:/data/keys/core.key
KOMODO_REPORTING_PRIVATE_KEY=file:/data/keys/reporting.key
## Allow Periphery to connect via its generated public key.
KOMODO_PERIPHERY_PUBLIC_KEY=file:/data/keys/periphery.pub

## Persist backups, sync files, and cloned repositories in the shared data volume.
KOMODO_CLI_BACKUPS_FOLDER=/data/backups
KOMODO_SYNC_DIRECTORY=/data/syncs
KOMODO_REPO_DIRECTORY=/data/repo-cache

## Persist Periphery identity and trust Core's generated public key.
PERIPHERY_PRIVATE_KEY=file:/data/keys/periphery.key
PERIPHERY_CORE_PUBLIC_KEYS=file:/data/keys/core.pub

## Specify the root directory used by Periphery agent.
## All your compose files and repos need to be inside this directory
## for Periphery to interact with them.
## - ROOT_DIRECTORY (/data)
## --- ./stacks
## ------ ./my_stack_1
## ------ ./my_stack_2
## --- ./repos
## ------ ./my_repo_1
## --- ./builds
## --- ./ssl
## --- ./file-manager-journal
PERIPHERY_ROOT_DIRECTORY=/data

## Docker's absolute named-volume storage root on the host.
## It is mounted read/write at the identical path so containerized Periphery
## can browse and modify local named volumes. Change this for rootless Docker
## or a nonstandard Docker data root; do not redirect it into /data.
PERIPHERY_DOCKER_VOLUME_ROOT=/var/lib/docker/volumes
```

For rootless Docker or a customized Docker data root, set `PERIPHERY_DOCKER_VOLUME_ROOT` to the value reported by:

```bash
docker info --format '{{.DockerRootDir}}/volumes'
```

:::warning Docker-volume File Manager access
The v3 Compose bind mount gives containerized Periphery read/write access to Docker's named-volume root. Keep the source and target at the same absolute path. If you do not want Periphery to manage named-volume files, remove that bind mount from the Compose file; stack file management remains available, while Docker-volume targets report that the capability is unavailable.
:::

The v3 templates also assign stable, explicit container names. Both database variants use `komodo-core` and `komodo-periphery`; MongoDB uses `komodo-mongo`, while FerretDB uses `komodo-postgres` and `komodo-ferretdb`. Update scripts, monitoring, or backup commands that refer to the old Compose-generated container names.

### 4. Start Komodo v3

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
```

Before considering the migration complete, verify that:

- Existing users can log in and resources, stacks, repositories, builds, backups, and server connections are present.
- The Stack File Manager can browse a managed stack.
- The Docker-volume File Manager can browse a named volume when its read/write bind mount is enabled. If it is unavailable, confirm that `PERIPHERY_DOCKER_VOLUME_ROOT` matches the host path reported by Docker and is mounted at that identical path inside Periphery.
