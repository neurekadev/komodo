title: Users, Groups, and Permissions
description: Give people and teams the Komodo access they need.

Use User Groups to grant a team's access once, then add or remove members as needed. You must be an administrator to enable accounts and manage other users' access.

## Control registration and default access

By default, users can register through an enabled login provider, but an administrator must enable their accounts. Enabled non-admin users start without access to existing resources unless a resource or group grants it. They can create some resource types unless you restrict creation.

1. Back up the main installation's `.env` and add the overrides you need from the tables below.
2. Run `docker compose -p komodo config --quiet`, then `docker compose -p komodo up -d komodo` to reload Core. A restart alone does not reload `.env`.
3. Use a private browser window to check the intended registration behavior. Sign in as an existing non-admin user to verify resource visibility and creation access.

### Registration and approval

| Environment variable | Default | Effect |
| --- | --- | --- |
| `KOMODO_DISABLE_USER_REGISTRATION` | `false` | Set to `true` to block new self-registered accounts after the first user exists. Local and OIDC overrides take precedence for their providers; GitHub and Google follow this setting. |
| `KOMODO_DISABLE_LOCAL_USER_REGISTRATION` | Inherits the global registration setting | Set to `true` to hide **Sign Up** and block local username/password registration. Existing local accounts can still sign in while local authentication is enabled. |
| `KOMODO_DISABLE_OIDC_USER_REGISTRATION` | Inherits the global registration setting | Set to `true` to block new accounts through OIDC. Existing OIDC accounts can still sign in. |
| `KOMODO_ENABLE_NEW_USERS` | `false` | Set to `true` to enable newly registered accounts automatically. This skips administrator approval; it does not make users administrators or grant resource permissions. |

To close self-registration, add `KOMODO_DISABLE_USER_REGISTRATION=true` and remove any local or OIDC registration overrides from `.env` and mounted configuration so they inherit that setting. Initial administrator creation on an empty database remains possible.

To allow OIDC registration while blocking local signups, keep the OIDC provider enabled and add:

```dotenv
KOMODO_DISABLE_LOCAL_USER_REGISTRATION=true
KOMODO_DISABLE_OIDC_USER_REGISTRATION=false
```

Leave `KOMODO_ENABLE_NEW_USERS=false` when accounts should wait for approval in **Settings → Users**. Changing it affects future registrations; review existing accounts individually. For login providers and `KOMODO_LOCAL_AUTH`, see [Authentication and Providers](/administration/authentication-and-providers#configure-user-sign-in).

### Default resource access

| Environment variable | Default | Effect |
| --- | --- | --- |
| `KOMODO_TRANSPARENT_MODE` | `false` | Set to `true` to give every enabled user base Read access to all resources. Specific permissions such as File Manager remain separate. |
| `KOMODO_DISABLE_NON_ADMIN_CREATE` | `false` | Set to `true` to allow only administrators to create resources, even when a user has Server or Build creation permission. Existing resource permissions still apply. |

With non-admin creation allowed, Server and Build creation still require their separate user permissions, and administrator-only resource types remain restricted. Use direct or group grants for access to existing resources. Enable transparent mode only when every enabled user should see every resource; combined with automatic account approval, it makes that visibility available to anyone who can register.

If a setting appears ineffective, check for environment overrides of mounted configuration and recreate Core. For unexpectedly broad resource access, review the user's direct grants, groups, and resource base permissions.

## Grant access to a team

1. Open **Settings → Users** and enable approved accounts.
2. Create a User Group and add its members.
3. Grant a base level on the required resources, then add specific permissions from the table below.
4. Sign in as a team member and check an allowed operation and one that should be denied.

Users inherit grants from every group they belong to. An **Everyone** group applies to all users. If access is broader than expected, inspect direct grants, group membership, and resource-type grants before changing anything else.

## Permission levels

| Level | Allows |
| --- | --- |
| None | No resource visibility or access. The default for non-admins. |
| Read | View the resource and configuration. |
| Execute | Read and run actions, such as deployment or builds. |
| Write | Execute, change configuration, and delete the resource. |

## Specific permissions

| Permission | Adds access to |
| --- | --- |
| Backups | Snapshot listing and browsing with Read; backup and restore with Execute or Write. |
| FileManager | Browsing and downloads with Read or Execute; file changes with Write on writable targets. |
| Logs | Docker and Compose logs. |
| Inspect | Container details, including environments that may contain secrets. |
| Terminal | Host terminals when granted on a Server; container terminals on attached Stacks or Deployments. |
| Attach | Attaching workloads to a Server, Builds to a Builder, or dependent resources to a Build or Repo. |
| Processes | The Server's running process list. |

A Stack can inherit specific permissions from its Server, but still needs a base permission on the Stack. Volume access uses the Server's permissions. **Server FileManager permission covers every eligible named volume on that host**, including application data and credentials; it cannot be limited to one Volume. Private Komodo recovery storage remains unavailable in File Manager.

Cross-server restore also requires Execute and Backups on the destination Server. Creating a recovered Stack additionally requires Stack creation access. Repository configuration, fleet scheduling, and Core recovery are administrator-only. Granting Backups does not enroll a worker; administrators separately [approve trusted hosts](/administration/backups#configure-backups).

## Permissioning by resource type

Use a resource-type grant when a team should access all resources of that type. Resource-specific grants can add access for selected resources. For example, in a [Resource Sync](/features/resource-sync#user-group):

```toml
[[user_group]]
name = "operators"
users = ["alice", "bob"]
all.Stack = { level = "Read", specific = ["Logs"] }
permissions = [
  { target.type = "Stack", target.id = "web", level = "Execute" },
]
```

## Administration

The initial super administrator can use **Make Admin** on a user's page. Administrators have unrestricted resource access and can manage non-admin users.

Disable an account from **Settings → Users** to block its GUI and API access. Grant global Server or Build creation permission only when the user should create those resources; the [non-admin creation policy](#default-resource-access) must also allow it.
