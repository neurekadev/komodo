title: Legacy Database Backup and Restore
description: Use the compatibility database backup format and restore it safely.
---

This page documents the compatibility `BackupCoreDatabase` CLI/API format. For encrypted fleet-wide Core, Stack, and Volume protection, use [Komodo Backups](/administration/backups).

The legacy operation creates gzip-compressed database exports on disk and restores them with the [Komodo CLI](/reference/cli), which is packaged in the Core image. It retains the most recent 14 exports by default and remains available for independent recovery within the same fork version; it does not migrate upstream Komodo installations.

## Create and Verify a Backup

### Prerequisites

- The backup directory is on persistent storage with enough free space.
- You can access the Core container or a configured Komodo CLI.
- No database migration or destructive maintenance is in progress.

1. Trigger a backup from an explicitly configured **Backup Core Database** Procedure or run:

   ```bash
   docker exec komodo km database backup -y
   ```

2. Confirm a new timestamped folder appears beneath the configured backup directory.
3. Verify the gzip files are non-empty and copy the backup to storage outside the Komodo host.
4. Periodically restore a backup into an isolated database and confirm users and resources can be read.

The expected result is a dated, readable snapshot plus an off-host copy. If no snapshot appears, inspect the Procedure update or CLI output, confirm database connectivity, and check the backup path's permissions and free space.

<Callout title="Restore replaces data" type="warn">
  Stop automated writes, take one final backup, and verify the selected restore folder before restoring a production database.
</Callout>

## Scheduled Backup

New installs do not create a legacy backup Procedure. Older fork installations may still have a daily **Backup Core Database** [Procedure](/features/procedures-and-actions#procedures); Core warns while it remains enabled. If you intentionally need one, create it from this TOML:

```toml
[[procedure]]
name = "Backup Core Database"
description = "Triggers the Core database backup at the scheduled time."
tags = ["system"]
config.schedule = "Every day at 01:00"

[[procedure.config.stage]]
name = "Stage 1"
enabled = true
executions = [
  { execution.type = "BackupCoreDatabase", execution.params = {}, enabled = true }
]
```

<Callout title="Information" type="info">

You can integrate `BackupCoreDatabase` into other Procedures, for example to trigger
this process before launching a backup container. The example above is an ordinary
Procedure that you can create manually when the compatibility format is required.

</Callout>

## Backups

When Komodo takes a database backup, it creates a **folder named for the time the backup was taken**,
and dumps the gzip-compressed documents to files in this folder. 
The Compose startup profile and the Core image's `km` wrapper default `KOMODO_CLI_BACKUPS_FOLDER` to `/data/backups`. Backups are therefore stored in the shared `data:/data` volume, which Docker names `komodo_data` when using `docker compose -p komodo`.

Due to its larger size and relative unimportance, the `Stats` collection (containing historical server cpu / mem / disk usage)
is not included in dated backups. Just latest Stats are maintained at the top level of the backup folder.

In order to prevent unbounded growth, the backup process implements a pruning feature which will ensure
only the most recent 14 backup folders are kept. To change this number, set `max_backups` (`KOMODO_CLI_MAX_BACKUPS`)
in `core.config.toml`, `komodo.cli.toml`, or in the Core container environment.

```
# Folder structure
/data/backups
| 2025-08-12_03-00-01
| | Action.gz
| | Alerter.gz
| | ...
| 2025-08-13_03-00-01
| 2025-08-14_03-00-01
| ...
| Stats.gz
```

<Callout title="Warning" type="warn">

Currently no built-in encryption is supported,
so you may want to encrypt the files before backing up remotely if your backup solution doesn't support that natively.

</Callout>

### Export from the named volume

The named volume protects backups across container replacement, but it is still local to the Docker host. Export the backup directory to a host archive and then copy that archive to your off-host backup destination:

```bash
mkdir -p backup-export
docker run --rm \
  --mount type=volume,src=komodo_data,dst=/source,readonly \
  --mount type=bind,src="$(pwd)/backup-export",dst=/export \
  alpine:3.22 \
  tar -czf /export/komodo-backups.tar.gz -C /source backups
```

The helper mounts `komodo_data` read-only and does not modify the running deployment. Verify and transfer `backup-export/komodo-backups.tar.gz` using your normal off-host backup tooling.

## Remote Backups

Use the standalone CLI image to write a remote database backup onto the machine running Docker. The database must be reachable over a trusted private network or protected tunnel; do not expose an unauthenticated database port publicly.

Create `backup.env` with the database's existing credentials, replace the host and password, and protect it with `chmod 600 backup.env`:

```dotenv
# --[ DATABASE ]---------------------------------------------------------------

KOMODO_DATABASE_ADDRESS=REPLACE_WITH_HOST:27017
KOMODO_DATABASE_USERNAME=komodo
KOMODO_DATABASE_PASSWORD=REPLACE_WITH_PASSWORD
```

Create the host backup directory, then replace `/path/to/komodo/backups` below with its absolute path:

```bash
docker run --rm \
  --env-file ./backup.env \
  --mount type=bind,src=/path/to/komodo/backups,dst=/data/backups \
  ghcr.io/neurekadev/komodo-cli:3 \
  km database backup --backups-folder /data/backups -y
```

The container backs up once and exits. Confirm a timestamped folder appears in the host directory. Use a Procedure or Action for scheduling. If the database name is not `komodo`, also set `KOMODO_DATABASE_DB_NAME` in `backup.env`.

## Restore

Restore into a separate, empty database first. Create `restore.env` using the target's credentials and protect it with `chmod 600 restore.env`. Restore intentionally uses different variable names from backup:

```dotenv
# --[ RESTORE TARGET ]---------------------------------------------------------

KOMODO_CLI_DATABASE_TARGET_ADDRESS=REPLACE_WITH_HOST:27017
KOMODO_CLI_DATABASE_TARGET_USERNAME=komodo
KOMODO_CLI_DATABASE_TARGET_PASSWORD=REPLACE_WITH_PASSWORD
KOMODO_CLI_DATABASE_TARGET_DB_NAME=komodo-restore
```

Keep the target on a trusted private network or protected tunnel. Review its address and database name carefully before running:

```bash
docker run --rm -it \
  --env-file ./restore.env \
  --mount type=bind,src=/path/to/komodo/backups,dst=/data/backups,readonly \
  ghcr.io/neurekadev/komodo-cli:3 \
  km database restore --backups-folder /data/backups
```

The CLI prompts before restoring the most recent backup. To select a specific snapshot, add `--restore-folder` with its timestamped directory name. Verify users and resources with the same fork version before using the restored database. This utility does not migrate upstream Komodo data.

<Callout title="Warning" type="warn">

The restore process can be run multiple times with same backup files, and won't create any extra copies.
HOWEVER it will not "clear" the target database beforehand. If the restore database is already populated,
those old documents will also remain. You may want to drop / delete the target database
before restoring to it in this case.

</Callout>

## Consistency

So long as the backup process completes successfully, the files produced can always be restored
no matter how active the Komodo instance is at the time of backup. However writes that happen during
the backup process, such as updates to the resource configuration, may or may not be included in the backup
depending on the timing.

While it should be rare that this causes any kind of issue when it comes to restoring, if your
Komodo undergoes a lot of usage at all hours and you are worried about consistency,
you could consider [locking](https://www.mongodb.com/docs/manual/reference/method/db.fsyncLock/#mongodb-method-db.fsyncLock)
Mongo before the backup. Just make sure to [unlock](https://www.mongodb.com/docs/manual/reference/method/db.fsyncUnlock/)
the database afterwards.
