Komodo Backups protects **Core**, **Stacks**, and **Docker volumes** with one schedule. Core coordinates the job across every configured Periphery, while the active primary repository remains the source of truth for what can be browsed or restored.

<Callout title="Vykar maturity" type="warn">
Komodo uses the pinned Rust libraries from [Vykar v0.19.1](https://github.com/borgbase/vykar/tree/v0.19.1) directly; no `vykar` command is required on Core or Periphery. Vykar's own project currently says it is not production-ready. Komodo adds encryption requirements, manifests, verification, transactional restore, and conservative maintenance, but administrators should evaluate that upstream maturity warning for their environment and keep an independently tested recovery path.
</Callout>

## Quick setup

1. Open **Backups** in the main navigation.
2. Configure an encrypted **Primary** repository. Core-local is the simplest choice; S3-compatible, SFTP, and Vykar REST repositories are also supported.
3. Optionally configure a **Mirror** in a different failure domain.
4. Choose one schedule and timezone, then enable Core, Stacks, and/or Volumes.
5. Choose how many complete snapshots to retain for each category. The value applies separately to Core, every Stack, and every Server/Volume pair.
6. Keep **Stop affected containers while backing up** enabled unless your applications provide their own consistency guarantees.
7. Review the bind-mount and anonymous-volume safety controls under **What to protect**.
8. Select **Save settings**. If you added a Core-local mirror or changed a Core-local path, restart Core now so its Periphery endpoints use the saved locations.
9. Select **Initialize repositories**, then **Back up fleet now**. Check **Fleet status** for partial nodes or integrity failures.

Save form changes before initializing, verifying, promoting a mirror, or starting a manual backup. Those actions are disabled while displayed settings are unsaved or being saved, so they cannot act on an older repository or protection policy.

Defaults are daily at 01:00 in the Core timezone, 14 complete backups per category, all eligible named resources included, and safe container stopping enabled. Cross-filesystem mount content and anonymous Docker volumes are excluded unless explicitly enabled.

## What is backed up

### Core

A Core backup is a consistent, versioned export of Komodo's restorable database collections. Authentication requests, including account creation, password changes, linked logins, passkeys, and MFA updates, wait while the logical export holds its snapshot barrier. It is a control-plane backup, not an operating-system image. Secrets used to access repositories, including encryption passphrases, are sealed with a persistent Core key and are never returned by the API or included in Core exports. Back up `/core-secrets/backup.key` separately with the deployment configuration; Core snapshots intentionally do not contain that key.

### Stacks

A Stack backup contains its Compose run directory and eligible normalized local bind-mount source roots. Docker named volumes are intentionally excluded because each is backed up and retained independently as a Volume. Swarm Stacks are rejected in this version.

By default, Komodo does not cross a filesystem boundary beneath any backup source, and it omits an explicit bind source when that source is on a different filesystem from the Stack run directory. This prevents rclone, FUSE, NFS, and similar mounts from being copied unexpectedly. Enable **Include cross-filesystem mount content** only when those mounted files are intentionally part of the backup. The Compose run directory itself is always included; this toggle and the bind rules only control bind-mount source roots.

The **Bind mount include patterns** and **Bind mount exclude patterns** fields accept one Vykar/gitignore-style rule per line and match the absolute bind source path. An empty include field permits every otherwise eligible bind root. Excludes are evaluated after includes and take precedence. Rules select whole bind roots, not individual files inside those roots; use `!` negation with the usual gitignore semantics when a rule set needs an exception. For example:

```text
# Include patterns
/srv/apps/**
!/srv/apps/temporary/**

# Exclude patterns
/mnt/rclone/**
**/.cache/**
```

Pattern selection and filesystem-boundary protection are independent: a path must pass the patterns, and cross-filesystem content still requires the toggle.

### Volumes

Every eligible local Docker named volume is included by default, including volumes not managed by a Komodo Stack. Anonymous volumes are excluded by default; enable **Include anonymous Docker volumes** to include them in fleet discovery and direct Volume backups. Komodo recognizes Docker's internal `com.docker.volume.anonymous` label and also treats the daemon-generated 64-character lowercase hexadecimal name form as anonymous for older Docker creation paths that omitted the label. Ordinary unlabeled named volumes remain included.

Komodo checks the driver and mountpoint again at backup time. Docker mounts that expose a configured Core-local repository are excluded so a repository cannot recursively back up itself. Remote/plugin volume drivers and non-local volume scope are rejected in this version.

Use **All**, **Include**, or **Exclude** selection for Stacks and Volumes. Volumes are identified directly by Server and Docker volume name, so unmanaged volumes can be selected without inventing a Stack association. Core has no include/exclude filter.

An explicitly included Stack or Volume that is missing or unsupported makes the fleet run partial rather than silently disappearing from the requested protection set.

## Backing up a fleet

At the beginning of every run, Core discovers the currently configured Periphery nodes and resolves live Docker state. New nodes join the next run automatically. A disconnected or failed node makes the fleet run partial or failed, but successful snapshots remain valid while failed work retries with exponential backoff for at most eight attempts. An exhausted run finishes as partial so later scheduled backups can protect healthy targets again; retention, verification, and compaction are still queued for the snapshots that succeeded.

File-manager uploads wait while a fleet backup or restore holds the mutation barrier, even if their upload ticket was created earlier. An upload already transferring keeps the barrier until Periphery confirms completion, so the protected operation waits for it to finish.

Backup operations never overlap. If a backup, retry, restore, repository maintenance operation, or another serialized backup operation is still active when a scheduled occurrence arrives, Core skips that occurrence without queuing or cancelling anything. The active work continues and the scheduler waits for the next normal occurrence. Manual backup requests wait for the current operation rather than creating concurrent repository writers.

If safe container stopping is enabled, Komodo calculates the affected running containers once per node, durably records and stops that set, writes the primary and mirror while the data is quiesced, and restarts exactly the containers that were previously running. A retry with the same run ID merges its newly discovered set into the existing restart journal, so a lost response cannot discard an earlier restart failure. Missing or unreadable files make a snapshot partial even when Vykar can commit it. Partial snapshots remain visible for diagnosis, never count as retained complete snapshots, and cannot be restored silently.

Every snapshot has a stable source label and a Komodo manifest:

```text
komodo/v1/core/<core-instance-id>
komodo/v1/stack/<stack-id>
komodo/v1/volume/<server-id>/<volume-name>
```

Each Periphery also has a stable Vykar hostname so snapshots remain attributable after resource names change.

Backup manifests record the running product's build version, as shown by Core, rather than Cargo's internal `0.0.0` workspace placeholder. Core recovery compares that recorded version with the running build before activating a restored database.

Core snapshot authorization also binds the snapshot identity to a digest of the exact export file names and contents, including its manifest. Recovery verifies that digest before importing any database records; reusing an older authorized snapshot name cannot authorize replacement contents. Legacy Core snapshots without this content-bound authorization remain visible as unbound snapshots and are not eligible for automatic Core recovery. Create a fresh Core snapshot with this version before relying on the recovery workflow.

Fleet run status polls every 15 seconds, while repository health and mirror lag share a five-minute cache across browsers. Snapshot inventories are loaded on demand; use **Refresh inventory** or **Refresh snapshots** to fetch new repository contents.

Critical operational alerts survive Core restarts in `/data/backup-operational-alert.json`. They remain latched until an operator confirms that the affected workloads and Periphery restore/quiesce journals have recovered. After that verification, stop Core, archive the alert file, and restart Core to acknowledge it; do not clear it while containers remain stopped or a restore is indeterminate.

## Restore a Stack or Volume

Open the resource's **Backups** tab, choose a complete snapshot, and select **Restore**. Administrators can also select **Recover** beside any complete Stack or Volume snapshot in the primary inventory on **Backups**. That inventory remains available after the original resource is deleted: Stack recovery creates a new recovered Stack, while Volume recovery lets you select the destination Server and volume. Leave the picker empty for a full restore, or expand folders and select multiple files and directories. The tree starts fully collapsed and loads from the primary repository as you expand it.

Before confirmation, Komodo lists paths that will be created, overwritten, and deleted, plus containers that will stop. A Volume restore stops every running container that mounts the destination volume, even when those containers belong to different Stacks. A Stack restore stops every running container in the deployed Compose project and every other container whose bind or named-volume storage overlaps a destination path. Containers that were already stopped remain stopped. Restore data is written to staging on the destination filesystem, verified with its metadata, and then published using a persisted rollback journal and directory synchronization. Komodo restarts exactly the previously running containers after successful publication or a proven rollback. If state becomes indeterminate, they remain stopped and Komodo raises a critical recovery alert.

Restore preflight and execution both reject any destination that overlaps a configured Core-local repository, including the matching repository subtree in a bind mount or named volume attached to Core. Repository aliases are resolved only from the Docker container identity reported by Core, then translated through Periphery's own mounts where necessary. A remote application's unrelated `/data` mount is not treated as Core storage. Keep Docker's `/etc/hostname` mount or its default container-ID hostname available; if Komodo cannot identify its container safely, protection fails with an explicit error. Other directories in the same shared volume remain available as backup and restore roots. This prevents Volume recovery and recovered Stack bind mappings from replacing the active backup repository.

The preview treats destination symlinks as entries to replace, not directories to traverse. Files behind those links are neither listed as deleted nor changed by replacing the link.

For selected files or folders, Komodo retains the original confirmed destination root and rejects any symlink ancestor between that root and the selection. The selected entry itself may be a symlink that will be replaced. This is checked during preflight and again before publication; old selection plans without the root boundary require a fresh preview.

When a restore creates a recovered Stack, Core marks that new resource with the restore-plan identity before it asks Periphery to commit the filesystem publication. Periphery retains the rollback journal and the final commit receipt until Core acknowledges the matching database state. After an interrupted Core or Periphery restart, Komodo reconciles that marker automatically; do not delete or repurpose the recovered Stack while reconciliation is pending.

Creating a preflight does not start a restore. Unexecuted plans expire after 15 minutes without contacting the destination or raising a recovery alert if that Server goes offline. Core durably marks execution before sending a publication request; only started or legacy plans with unknown execution state require restart reconciliation. A confirmed rollback clears that execution marker.

### Restore to another Periphery

The source Periphery does not need to be online. Choose any connected destination Periphery:

- A cross-node Stack restore requires a unique new Stack name and explicit absolute bind-path mappings. Komodo creates a recovered Stack; the original is not retargeted. Snapshot manifests retain absolute Compose symlink aliases. Environment-expanded bind sources such as `${DATA_ROOT}/cache` are matched by service and mount target to the snapshot's interpolated deployment metadata, then rewritten to the confirmed destination. Recovery does not re-expand them using the new host's environment; it fails before publication if the required deployment association is unavailable. Bind roots intentionally excluded from the snapshot have no destination mapping and remain unchanged.
- A cross-node Volume restore creates a new local volume, unless you explicitly confirm restoring into an existing local destination volume.
- A resource-tab same-node restore defaults to the original location. The administrator inventory asks for a destination volume name even on the original Server, so it can recover a deleted Volume under a new name. Explicitly selecting any existing volume requires the existing-destination confirmation, including the original Server and volume name.

After recovery, review application-specific ownership, external databases, DNS, secrets, and hardware dependencies before starting unrelated workloads.

## Recover Core on a fresh install

The original `/core-secrets/backup.key` is required before Komodo can identify or decrypt a Core snapshot. It authenticates snapshot identities and opens the repository credentials stored in the restored database. The official Compose templates keep it in the Core-only `core-secrets` volume rather than the `/data` volume shared with Periphery.

1. Stop the fresh Core before connecting the old repository.
2. Replace the fresh installation's generated `/core-secrets/backup.key` in the persistent `core-secrets` volume with the separately retained key from the original installation. Keep the file readable only by the Core service account.
3. Start Core again. Core loads this key only at process startup, so copying it into a running container is not sufficient.
4. Connect the existing primary repository in **Backups**, then select a Core snapshot under **Core recovery**.

Komodo restores the snapshot into a validation database, checks the backup schema/version and confirms that an administrator account remains available. It then switches the persisted active-database pointer and restarts. The fresh pre-restore database is retained for rollback.

If the restored database contains a pending Stack recovery record with its matching recovered Stack already inserted, Komodo normalizes it to the idempotent acknowledgement phase. Startup can then clear that historical record even if Periphery already discarded its completed receipt. Unmatched records retain the normal reconciliation checks; a contradictory receipt still blocks completion.

### Roll back a Core recovery

If the recovered Core starts but its application data or authentication configuration is unusable, roll back before making further changes:

1. Stop Core and take an independent backup of the database service. Do not run another Core against either database while changing the pointer.
2. Open `/data/backup-recovery-activation.json` in Core's persistent `data` volume. Confirm that `database` names the recovered database and that `previous_database` names the retained pre-recovery database. Stop if `previous_database` is absent or does not match the database you intend to restore.
3. Preserve a copy of the activation file. Replace it atomically with valid JSON that moves the current `database` value to `previous_database`, moves the old `previous_database` value to `database`, and leaves `core_instance_id` unchanged. Keep the file owner and mode unchanged.
4. Start Core. Its startup log must say it is using the retained database named in the updated `database` field.
5. Sign in with an administrator account, confirm expected Servers and Stacks are present, open **Backups**, and verify the primary repository before re-enabling scheduled work.

To return to the recovered database after diagnosing the problem, repeat the stopped-Core pointer swap; never edit the activation record while Core is running.

Do not point two active Core instances at the same database. After recovery, reconnect Periphery nodes and verify the repository before allowing scheduled pruning.

## Primary and mirror behavior

The primary repository is authoritative. Snapshot lists, manifests, file trees, and restores always come from the active primary backend. The mirror receives the same logical sources while data is quiesced, but it is not an automatic read fallback. Promotion is administrator-only and requires a successful full verification, making an incomplete mirror unable to silently become authoritative.

After initialization, a Core-local repository is the same location only when its resolved path is equal. Moving to a parent or child directory is a location change and requires verified promotion; overlapping primary and mirror paths remain forbidden.

<Callout title="Periphery backup-read trust" type="warn">
Vykar encrypts and deduplicates on the client, so every Periphery that writes to a shared repository receives its encryption passphrase and the worker-scoped storage access needed to read repository metadata and packs. The passphrase protects backups from the storage provider; it does not isolate one participating Periphery from another or from Core snapshots in the same repository. Treat every participating Server as backup-read trusted. If hosts must not share that trust, manage them with separate Komodo deployments and separate repositories.
</Callout>

Periphery never receives the Core backup authentication key and therefore cannot mint trusted source identities from its repository credentials alone. The official colocated agent still controls its Docker host through the socket and must be treated as host-trusted; use a remote Periphery or a separate host when that boundary matters.

For an off-site mirror, use a different provider or failure domain. Core-local storage is exposed to Periphery through separate authenticated embedded [`vykar-server`](https://vykar.borgbase.com/server-setup) endpoints for primary and mirror storage, which also enables server-side encrypted repacking. Restart Core after adding a Core-local mirror, changing a Core-local path, or promoting a Core-local mirror; Komodo blocks Periphery access until the endpoint matches the saved role.

## Retention, compaction, and verification

Retention is evaluated independently for Core, each Stack, and each Server/Volume pair in both repositories. Komodo batches all snapshot deletions first and compacts once per repository, rather than downloading and repacking separately for every volume. Manual backups and fleet retries that finish complete or partial feed a debounced maintenance queue for the same reason.

Queued maintenance loads the current repository and retention settings only after acquiring its operation and repository-role locks. Settings saved while it waits are used by that cycle; settings cannot change during its verification and deletion work.

Komodo uses Vykar's 20% dead-data compaction threshold. S3 and SFTP repacking is client-side and defaults to a 5 GiB per-cycle cap to control download cost; Core-local and REST repositories can use [server-side encrypted passthrough](https://vykar.borgbase.com/server-setup). See Vykar's [compaction architecture](https://vykar.borgbase.com/architecture#compact) for the storage model.

Every cycle performs bounded integrity sampling. A full verification is due every 60 days and is mandatory before mirror promotion. Structural failures block pruning and compaction so damaged repository state is never followed by destructive maintenance.

## Permissions

Backups require both a base resource level and the `Backups` specific permission:

- **Read + Backups** lists and browses snapshots the user may access.
- **Execute or Write + Backups** permits manual backup and same-target restore.
- A Volume uses its Server permission. A Stack accepts a direct grant or an inherited Server grant.
- New Server and Stack creators receive `Backups` automatically; existing permissions are not broadened during upgrade.
- Cross-node restore additionally requires **Execute + Backups** on the destination Server. Any restore that creates a recovered Stack requires the same destination Server permission, even when restoring onto the snapshot's historical Server, plus the existing Stack-create permission.
- Repository settings, schedules, retention, Core recovery, unbound snapshots, mirror promotion, and maintenance are administrator-only.

Repository credentials and encryption keys are never exposed through these grants. See [Users, Groups, and Permissions](/administration/users-groups-permissions#specific-permissions).

## Backend notes

Vykar supports [local, S3-compatible, SFTP, and REST backends](https://vykar.borgbase.com/backends). Komodo presents a typed setup form for each:

- **Core-local:** use a normalized absolute path on persistent Core storage, without surrounding whitespace, `.` or `..` components, duplicate separators, or a trailing separator. This is operationally simple but must be copied or mirrored off the Core host to survive host loss.
- **S3-compatible:** enter the full bucket/prefix URL, region, Core maintenance credentials, and distinct worker credentials. Backblaze B2 and other compatible providers can be used.
- **SFTP:** pin known-hosts data and paste complete multiline OpenSSH keys into the Core and worker key editors, preserving their line breaks. Use separate keys, each limited to the repository path. Configured keys remain hidden; an empty editor preserves the saved key.
- **REST:** use TLS and separate Core and worker access tokens. Plain HTTP requires an explicit opt-in and should only be used on a trusted private network.

For every external backend, the worker identity must be distinct and its storage-side policy must permit the reads and writes needed for backups while denying deletion, compaction, and other maintenance. Only Core receives the authoritative maintenance-capable credentials.

Encryption is mandatory on every repository. Store the persisted Core-only `/core-secrets/backup.key` with the rest of your disaster-recovery material; losing both Core state and this key prevents Komodo from unsealing repository credentials. On upgrade, Core migrates an existing `/data/keys/backup.key` into the Core-only location and removes the shared copy after the new file is durable.

## Vykar cache persistence

The official Compose files persist Vykar's cache in the existing named `data` volume. Core uses `/data/backups/.komodo-vykar-cache`; the colocated Periphery uses `.komodo-vykar` beneath its Stack directory, whose default host path is an alias into the same `data` volume. No separate cache volume is required. The cache can be rebuilt from a repository, but keeping it across container recreation avoids unnecessary index downloads and preserves normal deduplication performance.

## Legacy database backup migration

The older `BackupCoreDatabase` CLI/API operation remains available for compatibility, but new installs no longer create its scheduled Procedure. If an existing install still schedules it, Core emits a warning. Disable that Procedure after you have configured Komodo Backups, completed a Core snapshot, and tested a restore. The legacy format is documented under [Legacy Core database backups](/administration/backup-restore).
