Additional configuration options for Komodo Core and Periphery, including custom certificate authorities, OAuth/OIDC providers, and mounted config files.

## Find an environment variable

You can add supported optional variables to your deployment's `.env`. The installation examples contain required inputs; omitted settings use application or Compose startup defaults.

Use the `Env:` and `Default:` descriptions in the configuration references to find a variable's exact name, value format, and behavior:

- [Core configuration](https://github.com/neurekadev/komodo/blob/main/config/core.config.toml): login providers, registration, permissions, UI behavior, polling intervals, logging, and AWS credentials.
- [Periphery configuration](https://github.com/neurekadev/komodo/blob/main/config/periphery.config.toml): terminal controls, disk filters, logging, connections, and working directories.
- [CLI configuration](https://github.com/neurekadev/komodo/blob/main/config/komodo.cli.toml): CLI connections, database access, and export paths.

For registration switches and default permissions, follow [Control registration and default access](/administration/users-groups-permissions#control-registration-and-default-access). The Compose startup commands also supply [deployment defaults](https://github.com/neurekadev/komodo/blob/main/bin/compose-defaults.sh), including local authentication enabled and persistent key/workspace paths; these can differ from the standalone application defaults in the TOML references.

## Change Configuration Safely

1. Start from the [installation examples](/quick-start/install-komodo) and the current [`core.config.toml`](https://github.com/neurekadev/komodo/blob/main/config/core.config.toml) or [`periphery.config.toml`](https://github.com/neurekadev/komodo/blob/main/config/periphery.config.toml).
2. Back up the active Compose, environment, and mounted configuration files.
3. Change one concern at a time and keep secrets in protected files or secret-specific environment-file variables.
4. Run `docker compose -p komodo config`, recreate the affected service with `docker compose -p komodo up -d <service>`, and inspect its logs. A restart alone does not reload `.env`.
5. Verify sign-in, server connectivity, and one read-only operation before making another change.

The expected result is a healthy Core and connected Periphery agents using the new value. If the service fails, restore the previous file, re-run `docker compose -p komodo config`, and recreate it before continuing. For required environment inputs, image defaults, and storage paths, see [Container Deployment](/administration/container-deployment).

## First Server and Container Routing

`KOMODO_FIRST_SERVER_ADDRESS` is optional and selects an inbound connection to
the first Server. The main Compose installation instead uses an outbound local
Periphery connection. After startup, confirm the Server reports **OK**.

Set `KOMODO_INTERNET_INTERFACE` only when containerized Core must route outbound
traffic through a specific interface. The container needs the `NET_ADMIN`
capability for this setting. Leave the value empty to keep the container's
existing default route.

## Custom Certificate Authorities

In order to communicate with companion services on private networks,
such as OIDC and git providers,
**Komodo Core and Periphery may both need to trust one or more custom CAs**.

Both the Komodo Core and Periphery images automatically run `update-ca-certificates` on startup;
just mount any required root certificates inside `/usr/local/share/ca-certificates`:

```yaml
    volumes:
      ## ... (unchanged)
      ## Mount custom root CA certificates to trust individually
      - /path/to/root_ca1.crt:/usr/local/share/ca-certificates/root_ca1.crt
      - /path/to/root_ca2.crt:/usr/local/share/ca-certificates/root_ca2.crt
      ## OR the whole folder is fine too.
      - /path/to/custom-certs:/usr/local/share/ca-certificates
```

## Limit Periphery IPs

If using a reverse proxy with Komodo Core, you can limit the IPs which can connect to the Periphery endpoint. For example with Caddy:

```nginx
(reject-ips) {
	@externalIp not remote_ip 192.168.0.0/16 12.34.56.78/32
	respond @externalIp 403
}

komodo.example.com {
	handle /ws/periphery {
		import reject-ips
		reverse_proxy komodo:9120
	}
	handle {
		reverse_proxy komodo:9120
	}
}
```
<Callout title="Note" type="info">

Your reverse proxy should set `X-FORWARDED-HOST` header to your Komodo Core domain, which caddy does by default.

</Callout>

## Mount a Config File

If you prefer to keep sensitive information out of environment variables, you can optionally
write a config file on your host, and mount it to `/config/config.toml` in the Komodo core container.

The configuration can also be passed as **YAML** or **JSON**.
You can use it-tools to convert this TOML file to your preferred format:
  - YAML: https://it-tools.tech/toml-to-yaml
  - JSON: https://it-tools.tech/toml-to-json

<Callout title="Information" type="info">

Configuration can still be passed in environment variables, and will take precedent over what is passed in the file.

</Callout>

Quick download to `./komodo/core.config.toml`:
```bash
wget -P komodo https://raw.githubusercontent.com/neurekadev/komodo/main/config/core.config.toml
```

[View the current Core configuration example](https://github.com/neurekadev/komodo/blob/main/config/core.config.toml).
