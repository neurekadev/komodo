[MongoDB](https://www.mongodb.com) is Komodo's recommended database. It stores resource configuration, users, audit logs, and system state.

The official template uses the `mongo:8` major-version tag. This keeps installations on MongoDB 8 while allowing compatible patch updates when you pull the image.

## Install with MongoDB

Follow [Install Komodo](/quick-start/install-komodo) for the complete MongoDB, Core, and local Periphery installation.

The expected result is running `komodo-mongo`, `komodo-core`, and `komodo-periphery` containers. Database files persist in `komodo_mongo-data`; MongoDB configuration state persists in `komodo_mongo-config`.

## Update MongoDB 8

Back up Komodo before updating the database image, then run:

```bash
docker compose pull mongo
docker compose up -d
docker compose logs --tail=100 mongo
```

Confirm Core can reconnect and existing users and resources remain available. Do not delete the MongoDB volumes during an update.

## Troubleshooting

Start with:

```bash
docker compose ps
docker compose logs --tail=200 mongo
```

Verify the database credentials have not changed since the volume was initialized and that `komodo_mongo-data` is writable.

### MongoDB exits with code 139 on Linux 6.19 or newer

Some MongoDB 8 images can start successfully and then crash about 30–60 seconds later with exit code `139` (`SIGSEGV`) on affected Linux kernels starting with 6.19. This is a known restartable-sequences interaction between the kernel and MongoDB's TCMalloc configuration, tracked in [SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912). Some later MongoDB releases instead refuse to start on affected kernels. Check the [MongoDB kernel compatibility guidance](https://jira.mongodb.org/browse/SERVER-125742) for a fixed kernel and compatible MongoDB release; not every kernel newer than 6.19 is affected.

The affected Docker images explicitly set `GLIBC_TUNABLES=glibc.pthread.rseq=0`. The temporary workaround is **`1`, not `0`**: it overrides the image setting and restores glibc's rseq registration, avoiding the affected TCMalloc path. See the [docker-library investigation](https://github.com/docker-library/mongo/discussions/748) and the [glibc rseq tunable documentation](https://sourceware.org/glibc/manual/latest/html_node/POSIX-Thread-Tunables.html).

Confirm the signature before applying the workaround:

```bash
uname -r
docker inspect komodo-mongo --format 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
docker logs --tail=200 komodo-mongo
```

If the kernel is affected, add this temporary override beneath the MongoDB service's existing `environment` block:

```yaml
services:
  mongo:
    environment:
      # Temporary SERVER-121912 workaround: override the image's rseq=0.
      # Remove after upgrading to a fixed kernel and compatible MongoDB release.
      GLIBC_TUNABLES: glibc.pthread.rseq=1
```

Recreate only MongoDB and verify that it stays running:

```bash
docker compose up -d --force-recreate mongo
docker compose ps mongo
```

Check again after at least a minute and confirm Core can reconnect. This override is intentionally absent from the official template. It changes MongoDB's allocator behavior and can reduce performance; use it only for the matching crash signature, then remove it after installing a fixed kernel and compatible MongoDB release.

[View the MongoDB Compose template](https://github.com/neurekadev/komodo/blob/main/compose/mongo.compose.yaml) and [environment example](https://github.com/neurekadev/komodo/blob/main/compose/compose.env).
