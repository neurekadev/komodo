---
title: Migrate v2 to v3
description: Move supported Komodo v2 deployments to the v3 storage and configuration contract.
---


Komodo v3 changes the production Compose storage layout and the canonical host filenames. Review the [GitHub release](https://github.com/neurekadev/komodo/releases/tag/3.0.0) for the changelog when v3.0.0 is published.

<Callout title="Supported upstream boundary" type="warn">
  Upstream Komodo `v2.3.2` is the last supported upstream migration source. Do not use this procedure for a later upstream release; compatibility is not promised after the hard fork.
</Callout>

## Prerequisites

- The source deployment is Komodo v2, no newer than upstream `v2.3.2`.
- You can stop Core and every Periphery instance during the maintenance window.
- You have enough free space to keep both the original data and verified backups.
- You know whether the deployment uses MongoDB or FerretDB and whether Docker uses a nonstandard data root.

## File Manager

Komodo v3 adds a [File Manager](/features/file-manager) for Stack directories and Docker named volumes. It supports text editing, uploads and downloads, file and archive operations, conflict review, long-operation progress and cancellation, and per-user undo/redo journals.

Non-admin users need the new `FileManager` specific permission in addition to their base resource level. Read or Execute allows browsing, while Write allows changes on writable targets. Existing grants do not gain `FileManager` automatically; update the relevant users or groups. New Server and Stack creators receive it with their creator permissions.

The encrypted backup feature likewise requires the new `Backups` specific permission on Servers and Stacks. Existing grants are not broadened automatically; update users and groups that should browse or operate backups. New Server and Stack creators receive `Backups` with their creator permissions.

## Migrate to Komodo v3

The v3 templates share the Compose volume `komodo_data` between Core and Periphery at `/data`, and attach a separate `komodo_core-secrets` volume only to Core for backup authentication and sealing material. Existing MongoDB or FerretDB database volumes keep their v2 names.

<Callout title="Back up your deployment" type="error">

Back up the database, `/etc/komodo`, the `komodo_keys` volume, any existing `komodo_core-secrets` volume, and any custom configuration or certificates before continuing. The migration below moves files out of their v2 locations and assumes `komodo_data` does not already contain another deployment.

</Callout>

### 1. Stop Komodo v2

Run the original v2 command from the installation directory, without `-v`:

```bash
docker compose -p komodo -f mongo.compose.yaml --env-file compose.env down
```

If you use FerretDB, replace `mongo.compose.yaml` with `ferretdb.compose.yaml`.

### 2. Move the v2 data into `komodo_data`

Create the v3 data volume with the labels Compose uses to identify its project and volume:

```bash
docker volume create \
  --label com.docker.compose.project=komodo \
  --label com.docker.compose.volume=data \
  komodo_data
```

Use one temporary Alpine container to move the Periphery root and communication keys into the new layout:

```bash
docker run --rm \
  --mount type=bind,src=/etc/komodo,dst=/v2-root \
  --mount type=volume,src=komodo_keys,dst=/v2-keys \
  --mount type=volume,src=komodo_data,dst=/data \
  alpine:3.22 \
  sh -eu -c '
    find /v2-root -mindepth 1 -maxdepth 1 -exec mv {} /data/ \;
    mkdir -p /data/keys
    find /v2-keys -mindepth 1 -maxdepth 1 -exec mv {} /data/keys/ \;
  '
```

The helper container is removed when it finishes. If v2 used a different `PERIPHERY_ROOT_DIRECTORY`, replace `/etc/komodo` in the bind mount. Move any separately mounted sync files or other custom data into the matching directory beneath `/data` before starting v3.

### 3. Install the v3 files

Rename the existing environment file so Docker Compose discovers it automatically:

```bash
mv compose.env .env
```

Download the v3 MongoDB template under its canonical host filename:

```bash
curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/mongo.compose.yaml
```

For FerretDB, download `ferretdb.compose.yaml` instead:

```bash
curl -fsSL -o compose.yaml https://raw.githubusercontent.com/neurekadev/komodo/main/compose/ferretdb.compose.yaml
```

Keep the existing credentials and other operator settings in `.env`. Apply these storage-contract changes:

| Action | Variables |
| --- | --- |
| Remove | `COMPOSE_KOMODO_BACKUPS_PATH` |
| Change | `COMPOSE_KOMODO_IMAGE_TAG`, `KOMODO_PERIPHERY_PUBLIC_KEY`, `PERIPHERY_CORE_PUBLIC_KEYS`, `PERIPHERY_ROOT_DIRECTORY` |
| Add | `COMPOSE_PROJECT_NAME`, `KOMODO_PRIVATE_KEY`, `KOMODO_REPORTING_PRIVATE_KEY`, `KOMODO_CLI_BACKUPS_FOLDER`, `KOMODO_SYNC_DIRECTORY`, `KOMODO_REPO_DIRECTORY`, `PERIPHERY_PRIVATE_KEY`, `PERIPHERY_DOCKER_VOLUME_ROOT` |

Add or replace the settings using this exact block. Its comments and values match the current [`compose.env`](https://github.com/neurekadev/komodo/blob/main/compose/compose.env) example:

```dotenv
## Keep the established Compose project and named-volume prefix.
COMPOSE_PROJECT_NAME=komodo
## Follows "major.minor.patch" semver. Use the v3 major alias by default.
COMPOSE_KOMODO_IMAGE_TAG="3"

## Persist Core identity and reporting keys in the shared data volume.
KOMODO_PRIVATE_KEY=file:/data/keys/core.key
KOMODO_REPORTING_PRIVATE_KEY=file:/data/keys/reporting.key
## The backup key is generated under /core-secrets by Core and is not shared
## with Periphery. The Compose template persists that directory separately.
## Allow Periphery to connect via its generated public key.
KOMODO_PERIPHERY_PUBLIC_KEY=file:/data/keys/periphery.pub

## Persist backups, sync files, and cloned repositories in the shared data volume.
KOMODO_CLI_BACKUPS_FOLDER=/data/backups
KOMODO_SYNC_DIRECTORY=/data/syncs
KOMODO_REPO_DIRECTORY=/data/repo-cache

## Persist Periphery identity and trust Core's generated public key.
PERIPHERY_PRIVATE_KEY=file:/data/keys/periphery.key
PERIPHERY_CORE_PUBLIC_KEYS=file:/data/keys/core.pub

## Specify the root directory used by Periphery agent.
## All your compose files and repos need to be inside this directory
## for Periphery to interact with them.
## - ROOT_DIRECTORY (/data)
## --- ./stacks
## ------ ./my_stack_1
## ------ ./my_stack_2
## --- ./repos
## ------ ./my_repo_1
## --- ./builds
## --- ./ssl
## --- ./file-manager-journal
PERIPHERY_ROOT_DIRECTORY=/data

## Docker's absolute named-volume storage root on the host.
## It is mounted read/write at the identical path so containerized Periphery
## can browse and modify local named volumes. Change this for rootless Docker
## or a nonstandard Docker data root; do not redirect it into /data.
PERIPHERY_DOCKER_VOLUME_ROOT=/var/lib/docker/volumes
```

For rootless Docker or a customized Docker data root, set `PERIPHERY_DOCKER_VOLUME_ROOT` to the value reported by:

```bash
docker info --format '{{.DockerRootDir}}/volumes'
```

The templates keep `PERIPHERY_ROOT_DIRECTORY=/data` for keys, SSL files, and File Manager state. Repositories, stacks, and builds remain in the same `komodo_data` volume, but Periphery accesses them through host-visible aliases beneath `${PERIPHERY_DOCKER_VOLUME_ROOT}/komodo_data/_data`. This keeps relative Compose bind mounts and Docker build contexts in the host daemon's path namespace without changing the named-volume layout.

With the standard Docker volume root, `docker compose config` resolves the Periphery directories to:

```text
/var/lib/docker/volumes/komodo_data/_data/repos
/var/lib/docker/volumes/komodo_data/_data/stacks
/var/lib/docker/volumes/komodo_data/_data/builds
```

<Callout title="Periphery host path access" type="warn">

The v3 Compose bind mount gives containerized Periphery read/write access to Docker's entire named-volume root. Keep the source and target at the same absolute path. Read/write access is required for the host-visible repository, Stack, and build aliases as well as Docker-volume File Manager operations; changing it to read-only or mounting only `komodo_data` breaks that functionality.

This mount is a host-level trust boundary, not a per-volume allowlist. The File Manager API rejects roots that overlap its private journal, including filesystem aliases. The shared `komodo_data` volume remains listed but its Files tab is unavailable because it contains that journal and Periphery credentials. A Server-level `FileManager` permission covers every other eligible named volume on that Server. Periphery also has the Docker socket, so protect its Core connection and grant `FileManager` only to users trusted with all other named-volume data on the host. See [File Manager permissions](/features/file-manager#permissions).

</Callout>

The v3 templates also assign stable, explicit container names. Both database variants use `komodo-core` and `komodo-periphery`; MongoDB uses `komodo-mongo`, while FerretDB uses `komodo-postgres` and `komodo-ferretdb`. Update scripts, monitoring, or backup commands that refer to the old Compose-generated container names.

### 4. Start Komodo v3

```bash
docker compose config
docker compose up -d
docker compose ps
```

Before considering the migration complete, verify that:

- Existing users can log in and resources, stacks, repositories, builds, backups, and server connections are present.
- `docker compose config` shows `PERIPHERY_ROOT_DIRECTORY: /data` and the repository, stack, and build directories beneath Docker's actual `komodo_data` mountpoint.
- The Stack File Manager can browse a managed stack.
- The `komodo_data` Docker Volume remains listed, but its Files tab reports File Manager unavailable.
- The Docker-volume File Manager can browse a named volume when its read/write bind mount is enabled. If it is unavailable, confirm that `PERIPHERY_DOCKER_VOLUME_ROOT` matches the host path reported by Docker and is mounted at that identical path inside Periphery.

## Roll back

1. Stop the v3 project without `-v` so its volumes remain available for diagnosis.
2. Move the migrated `/data` files aside; do not merge them back into the v2 locations.
3. Restore the database, `/etc/komodo`, `komodo_keys`, Compose file, environment file, custom configuration, and certificates from the pre-migration backups.
4. Restore the exact v2 image tags and original storage mounts.
5. Start the v2 project and verify sign-in, resources, backups, and every server connection.

Keep the unused v3 volumes until the rollback is verified. Remove them only in a later, separately reviewed cleanup.
